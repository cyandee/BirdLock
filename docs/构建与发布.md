# 构建与发布

这页留给从源码构建或参与开发的朋友。日常使用直接下载[安装包](https://github.com/cyandee/BirdLock/releases/tag/v1.10.0)就好。

## 版本和依赖

Mac 与 Windows 共用根目录的 [VERSION](../VERSION)，显式指定构建版本时必须与该文件一致。1.5 及以上安装包已具备更新器。1.10 的 Mac 自动更新使用完整包，Windows 提供 1.9.0 基线文件增量及完整包兜底。发布时先核对并上传附件，确认可下载后再更新签名清单。[项目近况](工作进度.md)

- 鸟类模型为 YOLO11m 和 eye-pose-v0，两端分别使用 Core ML / ONNX。
- 飞机模型约 204 MB，不放进普通 Git。`python3 scripts/fetch_aircraft_model.py` 按固定版本、大小和 SHA256 下载；也可以用 `--source-file <模型文件>` 复用已有下载。文件校验不符时会保留并报错。
- Mac 的 `BirdLockAircraftRuntime` 固定使用 ONNX Runtime Swift 1.24.2 对应源码提交，具体版本见 Package.resolved。首次解析 SwiftPM 依赖需要联网。
- 音效在 [SharedResources/Audio](../SharedResources/Audio/README.md)，当前为 11 条连拍录音和 1 条单拍声。赞赏图片在 SharedResources/Support。
- 两端打包都会核对模型、音效和许可文件，再复制进应用。安装包内已包含运行所需模型，使用时不用下载。
- 镜头配置从固定 Gyroflow 目录选入 383 份（原有 8 份加 375 份），包含 CC0 许可和 SHA256 清单；`verify_bundle.py --lens-resources SharedResources/LensProfiles` 可独立校验。
- 陀螺仪读取组件使用固定版本 telemetry-parser，构建需要支持 Rust 2024 edition 的工具链。构建脚本调用 `scripts/prepare_telemetry_helper.py`，优先校验已暂存的完整组件，否则用 Cargo 构建。Mac 通用包需要 arm64/x86_64 两个目标；Windows 原生构建产生 x64 PE。可用 `BIRDLOCK_TELEMETRY_HELPER` 指定包含 manifest 与 Licenses 的完整预构建组件，校验不符会停止打包。详情见 [telemetry 构建说明](../tools/telemetry/README.md)。

## macOS 本地构建

使用完整 Xcode 的 Developer 目录。本次本地构建使用 Xcode 27.1 / Swift 6.4.2；已给光流能力检查加入新旧 SDK 兼容分支，云端工具链仍需单独验证。

```zsh
swift test
swift run birdlock-cli selftest
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r scripts/requirements-updates.txt
python -m unittest discover -s scripts/tests
UNIVERSAL=1 zsh scripts/build_app.sh
zsh scripts/make_dmg.sh
```

输出为 `dist/BirdLock.app`、`dist/BirdLock-1.10.0.dmg` 和 `.sha256`。`APP_OUTPUT` 可以指定另一输出目录，方便保留旧包。打包先放入模型、音效、HTML/PDF 手册、协议和许可，再签名。

目前使用临时签名，尚未做 Developer ID 签名和 Apple 公证。脚本中的 `SIGN_ID` 是签名入口，正式分发流程还没接完。

## Windows 本地构建

使用 Python 3.12 x64，安装 `windows/requirements.txt` 和 PyInstaller，详细命令见 [Windows 开发说明](../windows/README.md)。

```powershell
python windows/build_windows.py
```

输出为 `windows/dist/BirdLock/` 和 `windows/dist/BirdLock-1.10.0-Windows-x64.zip`。脚本会准备飞机权重、FFmpeg、文档和版本资源。

测试实际混音前要先准备好 FFmpeg。显卡推理、OpenCL 或硬件编码不可用时，程序可以回退到 CPU / 软件编码。

本轮因 Parallels 许可证过期，用户明确决定自行在 Windows 电脑测试。另提供仅限本轮 1.6.0 → 1.10.0 的本地候选组装脚本 [assemble_windows_local.py](../scripts/assemble_windows_local.py)：使用 Python 3.12、PyInstaller 6.22.3 与 pefile 2024.8.26，输入 SHA256 固定为 `628ccddf5214a1f9d8b1dc58a3c5608bc17bdee1279c98352211912f00fed1e4` 的既有 1.6.0 本地 Windows ZIP，输出必须是新目录。授权公开发布可加 `--release`，仅改变随包说明，不跳过源码、资源校验，也不会将未完成的Windows实机测试标为通过。

该脚本保留 Windows 启动器机器码、第三方字节码及原生依赖，重编当前 BirdLock 模块，更新 PE/资源版本，加入镜头库和已交叉编译的 Windows 遥测组件，并逐项验证源码、归档、DLL/PYD/模型、许可和 ZIP CRC。它不是通用的 PyInstaller 跨平台构建器，也不能替代 Windows 运行验收。常规后续版本仍应在 Windows 使用标准构建命令。

## Mac 包的完整性

我会以完整 DMG 分发 Mac 版，避免拆开应用后丢文件或权限。签名后修改包内文件也会破坏签名，因此缓存和偏好都放在应用之外。

[verify_mac_artifact.py](../scripts/verify_mac_artifact.py)会做以下检查：

1. 验证最终 DMG，或检查 ZIP 完整性。
2. 只读挂载或解包后，检查应用签名和启动文件权限。
3. 把整个应用复制到临时安装目录，再检查一次签名。
4. 确认检查前后的分发文件 SHA256 相同，最后卸载临时镜像。

检查过程不会启动应用、重签名或清除隔离标记。签名完整与 Apple 公证是两回事；原来的 UTF-8 启动报错还没复现，暂时不能确定原因。

传输时请保留整个 DMG，别在网盘里在线拆包后逐文件下载。下载后可对照 SHA256SUMS；不一致就重新下载，一致但打不开，请提供系统版本、芯片和具体错误。

参考：[Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/)、[Mac 分发打包说明](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution)。

## GitHub Actions

源码快速检查由 `pr-checks.yml` 执行。完整构建使用 `release.yml`，Windows 打包复用 `windows.yml`。[PR 工作流](../.github/workflows/pr-checks.yml) · [完整工作流](../.github/workflows/release.yml) · [Windows 打包](../.github/workflows/windows.yml)

| 触发方式 | 配置的行为 |
|---|---|
| 创建、重新打开或更新 PR | `macOS checks` 运行 Swift 单测、CLI 自检和打包工具单测。`Windows checks` 运行 Python 单测、FFmpeg 源码自检和 Qt 离屏启动 |
| 普通任务分支推送 | 已开 PR 时重跑快速检查 |
| `main` 更新，或手动在分支运行完整工作流 | 测试、双平台成品构建、源码归档和校验汇总，产物保存在 Actions |
| 经授权推送匹配 `VERSION` 的 `v*` 标签 | 完整构建通过后按既有逻辑创建 Release 草稿。带测试后缀的标签标为 prerelease |
| 手动运行 Windows 打包工作流 | Windows 成品、原生更新器验证、源码与成品自检及离屏截图 |
| 实体设备验收 | 在对应设备上运行 GUI、真实素材、显卡推理及相关安装升级测试，单独登记结果 |

汇总需要三个文件齐全且非空：`BirdLock-<版本>.dmg`、`BirdLock-<版本>-Windows-x64.zip`、`BirdLock-<版本>-source.zip`，然后生成 SHA256SUMS。已有同名 Release 就跳过创建，不覆盖里面的文件。

PR 使用只读权限并按 PR 取消过期运行。快速检查无需构建发布用 DMG、Windows ZIP、遥测辅助程序和原生更新器。托管硬件相关跳过项以及实体设备结果分别登记。维护者可在 GitHub 为 `main` 要求通过 PR 合并，并将 `macOS checks` 和 `Windows checks` 设为必需检查。[测试矩阵](development/TEST_MATRIX.md)

## 1.4.1 本地构建补充

Windows 构建脚本给隔离 Python 子进程显式加了 `-X utf8`，已能通过本地 Windows 打包。原来的云端 SDK 与运行环境问题仍以实际 Actions 结果为准，本地构建成功不能代替云端验证。

机头模型在 16 个及以上逻辑处理器上默认使用 8 个 CPU 线程，较小 CPU 最多 4 个，可用 `BIRDLOCK_AIRCRAFT_THREADS` 做诊断对照。鸟类沿用 ONNX Runtime 的默认线程策略，可用 `BIRDLOCK_CPU_THREADS` 临时覆盖；完整鸟类分析测试未显示固定 4 线程更快，因此没有设成默认。

Windows 的大量音轨或特写重复可能超过系统进程命令长度，这时会提示缩短路径或减少音轨/重复次数；本轮取消回归使用 8 次重复，另测了真实管道背压。

## 1.4.2 光流辅助进程与诊断

Mac 打包同时构建 `BirdLockInterpolation`，放到应用的 `Contents/MacOS/`，与主程序一起签名和检查。辅助进程只接收内存像素与插帧比例，不接收用户文件路径；异常退出或 60 秒无响应时，主程序结束辅助进程并使用帧混合，导出结果会显示提示。帧配置超出 VideoToolbox 范围也明确回退。

Mac 日志位于 `~/Library/Logs/BirdLock/`，可用 `BIRDLOCK_LOG_DIR` 在测试中隔离。Windows 沿用数据目录的滚动日志和原生崩溃堆栈。两端帮助菜单可导出 ZIP，默认隐藏用户目录，只收集日志和系统信息，不收集设置与照片。

回归需真实操作 Qt 编码与质量下拉框，不能只给内部参数赋值；还要测试光流进程崩溃、超时和正常补帧。

## 1.4.3 长序列回归

600 源帧压力测试需确保真正发生补帧，例如源 20 fps、输出 30 fps，不能仅选择光流却没有中间帧。使用重复样例时应明确说明，不能当作用户原片或真实识别精度验证。分别记录开/关光流、横/竖 2K、输出帧数、回退状态和主/辅助进程 RSS。RSS 不含单独核算的 GPU 与系统服务内存。

光流工作进程按累计处理像素回收：2K 每个进程最多处理 64 次插帧，大画面更少。只回收处理进程和渲染缓存，编码器与时间线保持连续。

## 自动更新的本地签名

1.5.0 接入 Sparkle 2.10.1 和 Windows 独立更新器。第一次仍需手动安装。更新清单、完整更新包与增量包由本机工具生成和签名，私钥不上 GitHub，也不放入 Actions Secrets。云端 workflow 只构建普通包，不会自动启用更新源。

发布步骤和签名参数见[自动更新](自动更新.md)。Mac 的 CFBundleVersion 与 VERSION 使用同一个数字版本；Windows 构建需要系统 .NET Framework 4.x 编译器，生成的更新器要求 .NET Framework 4.8。正式版与测试版均需提升数字版本。新的更新源只有在安装包和签名核验完成、我确认发布后才开放。

Windows 发布依赖用 `windows/constraints-release.txt` 固定到受测版本。打包安装命令为 `pip install -r windows/requirements.txt -c windows/constraints-release.txt pyinstaller`。升级依赖后需重新回归并更新约束，避免因环境漂移而下载整套运行库。原 requirements 保留开发兼容范围。
