# 构建与发布

这页留给从源码构建或参与开发的朋友。日常使用直接下载[安装包](https://github.com/cyandee/BirdLock/releases/tag/v1.5.0-beta.1)就好。

## 版本和依赖

Mac 与 Windows 共用根目录的 [VERSION](../VERSION)，当前两端源码与已发布测试包均为 1.5.0。构建时显式指定版本，必须与这个文件一致。本次安装包标签为 `v1.5.0-beta.1`，应用内显示 1.5.0。在线更新清单在 main 分支的 updates 目录维护，在资产上传核验后开放。

- 鸟类模型为 YOLO11m 和 eye-pose-v0，两端分别使用 Core ML / ONNX。
- 飞机模型约 204 MB，不放进普通 Git。`python3 scripts/fetch_aircraft_model.py` 按固定版本、大小和 SHA256 下载；也可以用 `--source-file <模型文件>` 复用已有下载。文件校验不符时会保留并报错。
- Mac 的 `BirdLockAircraftRuntime` 固定使用 ONNX Runtime Swift 1.24.2 对应源码提交，具体版本见 Package.resolved。首次解析 SwiftPM 依赖需要联网。
- 音效在 [SharedResources/Audio](../SharedResources/Audio/README.md)，当前为 11 条连拍录音和 1 条单拍声。赞赏图片在 SharedResources/Support。
- 两端打包都会核对模型、音效和许可文件，再复制进应用。安装包内已包含运行所需模型，使用时不用下载。

## macOS 本地构建

使用完整 Xcode 的 Developer 目录。本次本地构建使用 Xcode 27.1；已给光流能力检查加入新旧 SDK 兼容分支，云端工具链仍需单独验证。

```zsh
swift test
python3 -m unittest discover -s scripts/tests
UNIVERSAL=1 zsh scripts/build_app.sh
zsh scripts/make_dmg.sh
```

输出为 `dist/BirdLock.app`、`dist/BirdLock-1.5.0.dmg` 和 `.sha256`。`APP_OUTPUT` 可以指定另一输出目录，方便保留旧包。打包先放入模型、音效、HTML/PDF 手册、协议和许可，再签名。

目前使用临时签名，尚未做 Developer ID 签名和 Apple 公证。脚本中的 `SIGN_ID` 是签名入口，正式分发流程还没接完。

## Windows 本地构建

使用 Python 3.12 x64，安装 `windows/requirements.txt` 和 PyInstaller，详细命令见 [Windows 开发说明](../windows/README.md)。

```powershell
python windows/build_windows.py
```

输出为 `windows/dist/BirdLock/` 和 `windows/dist/BirdLock-1.5.0-Windows-x64.zip`。脚本会准备飞机权重、FFmpeg、文档和版本资源。

测试实际混音前要先准备好 FFmpeg。显卡推理、OpenCL 或硬件编码不可用时，程序可以回退到 CPU / 软件编码。

## Mac 包的完整性

我会以完整 DMG 分发 Mac 版，避免拆开应用后丢文件或权限。签名后修改包内文件也会破坏签名，因此缓存和偏好都放在应用之外。

[verify_mac_artifact.py](../scripts/verify_mac_artifact.py)会做以下检查：

1. 验证最终 DMG，或检查 ZIP 完整性。
2. 只读挂载或解包后，检查应用签名和启动文件权限。
3. 把整个应用复制到临时安装目录，再检查一次签名。
4. 确认检查前后的分发文件 SHA256 相同，最后卸载临时镜像。

检查过程不会启动应用、重签名或清除隔离标记。签名完整与 Apple 公证是两回事；原来的 UTF-8 启动报错还没复现，暂时不能确定原因。

传输时请保留整个 DMG，别在网盘里在线拆包后逐文件下载。下载后可对照 SHA256SUMS；不一致就重新下载，一致但打不开，请提供系统版本、芯片和具体错误。

参考：[Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/)、[Mac 分发打包说明](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution)。

## GitHub Actions

统一入口是 [release.yml](../.github/workflows/release.yml)，Windows 部分复用 [windows.yml](../.github/workflows/windows.yml)。

| 触发方式 | 配置的行为 |
|---|---|
| 普通分支推送 | 不触发打包 |
| 手动运行统一 workflow | 测试、双平台构建、源码归档和校验汇总，生成 Actions 产物 |
| 推送匹配 VERSION 的 `v*` 标签 | 构建成功后创建同一个 Release 草稿；带测试后缀的标签标为 prerelease |
| 单独运行 Windows workflow | 只生成 Windows 产物 |

汇总需要三个文件齐全且非空：`BirdLock-<版本>.dmg`、`BirdLock-<版本>-Windows-x64.zip`、`BirdLock-<版本>-source.zip`，然后生成 SHA256SUMS。已有同名 Release 就跳过创建，不覆盖里面的文件。

**自动构建还没有跑通。** [1.4.0 的运行记录](https://github.com/cyandee/BirdLock/actions/runs/39193501761)中，Mac 是光流 API 的 SDK 差异，Windows 是隔离 Python 的中文输出编码问题。源码已加入 SDK 兼容分支和 `-X utf8`，本地构建通过。

[1.4.3 的运行记录](https://github.com/cyandee/BirdLock/actions/runs/40693720238)里，版本和源码归档成功，Mac 在测试与界面源码的数值类型推断处编译失败，Windows 在飞机许可文件校验处停止；没有进入双平台汇总或创建草稿的步骤。这次云端没有生成可用的双平台安装包，下载页使用下方说明的本地受测包。

1.4.3 下载页使用此前在本地测好的原包，发布前重新检查签名、ZIP 完整性和哈希。源码 ZIP 直接从本次发布标签生成，旧标签与安装包保留。包内手册是打包时的版本，后续文字调整可看在线文档。

## 1.4.1 本地构建补充

Windows 构建脚本给隔离 Python 子进程显式加了 `-X utf8`，已能通过本地 Windows 打包。原来的云端 SDK 与运行环境问题仍以实际 Actions 结果为准，本地构建成功不能代替云端验证。

机头模型在 16 个及以上逻辑处理器上默认使用 8 个 CPU 线程，较小 CPU 最多 4 个，可用 `BIRDLOCK_AIRCRAFT_THREADS` 做诊断对照。鸟类沿用 ONNX Runtime 的默认线程策略，可用 `BIRDLOCK_CPU_THREADS` 临时覆盖；完整鸟类分析测试未显示固定 4 线程更快，因此没有设成默认。

Windows 的大量音轨或特写重复可能超过系统进程命令长度，这时会提示缩短路径或减少音轨/重复次数；本轮取消回归使用 8 次重复，另测了真实管道背压。

## 1.4.2 光流辅助进程与诊断

Mac 打包同时构建 `BirdLockInterpolation`，放到应用的 `Contents/MacOS/`，与主程序一起签名和检查。辅助进程只接收内存像素与插帧比例，不接收用户文件路径；异常退出或 60 秒无响应时，主程序结束辅助进程并使用帧混合，导出结果会显示提示。帧配置超出 VideoToolbox 范围也明确回退。

Mac 日志位于 `~/Library/Logs/BirdLock/`，可用 `BIRDLOCK_LOG_DIR` 在测试中隔离。Windows 沿用数据目录的滚动日志和原生崩溃堆栈。两端帮助菜单可导出 ZIP，默认隐藏用户目录，只收集日志和系统信息，不收集设置与照片。

回归需真实操作 Qt 编码与质量下拉框，不能只给内部参数赋值；还要测试光流进程崩溃、超时和正常补帧。

## 1.4.3 长序列回归

600 源帧压力测试需确保真正发生补帧，例如源 20 fps、输出 30 fps，不能仅选择光流却没有中间帧。使用重复样例时应明确说明，不能当作用户原片或真实识别精度验证。分别记录开/关光流、横/竖 2K、输出帧数、回退状态和主/辅助进程 RSS。RSS 不含单独核算的 GPU 与系统服务内存。

光流工作进程按累计处理像素回收：2K 每个进程最多处理 64 次插帧，大画面更少。只回收处理进程和渲染缓存，编码器与时间线保持连续。

## 自动更新的本地签名

1.5.0 接入 Sparkle 2.10.1 和 Windows 独立更新器。第一次仍需手动安装。更新清单、完整更新包与增量包由本机工具生成和签名，私钥不上 GitHub，也不放入 Actions Secrets。云端 workflow 只构建普通包，不会自动启用更新源。

发布步骤和签名参数见[自动更新](自动更新.md)。Mac 的 CFBundleVersion 与 VERSION 使用同一个数字版本；Windows 构建需要系统 .NET Framework 4.x 编译器，生成的更新器要求 .NET Framework 4.8。正式版与测试版均需提升数字版本。新的更新源只有在安装包和签名核验完成、我确认发布后才开放。

Windows 发布依赖另用 `windows/constraints-release.txt` 固定到本地受测的版本：`pip install -r windows/requirements.txt -c windows/constraints-release.txt pyinstaller`。升级依赖后需重新回归并更新约束，避免仅因打包环境漂移而下载整套运行库。原 requirements 仍保留开发兼容范围。新增云端更新器回归步骤尚未实际运行，不把本地结果当作云端成功。

## 1.5.0 发布构建说明

本次 Release 使用本机已经受测的双平台包，刷新随包文档后重新签名与核验，没有更换模型、音效或运行库。标签触发的[云端构建](https://github.com/cyandee/BirdLock/actions/runs/41004519227)中，Windows 已完成打包和94项测试，但后续原生测试命令的路径参数解析失败；Mac 在 CLI 自测代码的一处长表达式上触发旧编译器类型推断超时。该次云端运行没有完成双平台汇总，未用于替换 Release 文件。后续 main 分支已拆分 CLI 表达式、改用绝对 Windows 路径；新运行的结果需另行确认，不把本机结果视为云端通过。

后续 [main 云端构建](https://github.com/cyandee/BirdLock/actions/runs/41010250475)已通过 Mac、Windows、源码归档和双平台汇总。CLI 与测试数据改为显式类型/分步表达式，原生测试使用绝对路径。托管 Mac 的硬件光流无法初始化时，两项颜色测试在显式 CI 开关下标记跳过；真实 Mac 仍必须实际通过。这次发布包的两项颜色测试及最终 helper 均在本机完成，云端产物没有覆盖 Release 附件。
