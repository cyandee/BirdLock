# 自动更新

BirdLock 正在接入自动更新。第一次需要手动安装带更新功能的版本，旧版无法凭空获得更新器。之后可以在软件里检查、下载并重启安装新版。照片识别和视频合成依然不需要联网。

## 两个平台怎么更新

Mac 使用 [Sparkle 2](https://sparkle-project.org/documentation/)。更新包和更新清单都签名，优先下载增量包，不适用时使用完整包。安装过程由 Sparkle 管理，正在分析或导出时暂缓检查和重启。

Windows 使用独立的小型更新器，利用系统的 .NET Framework 4.8，不额外打包一套 Python。先验证清单签名，再下载和校验每个文件。支持文件级增量、完整包兜底和下载续传。新版暂存完成后才退出旧版并替换程序，启动失败时恢复旧版。`data` 和不属于程序文件清单的用户文件保留在原位置。含目录链接或无法写入的目录会停止更新，请改用手动安装。

两端都可以选择接收测试版。关闭自动检查后，仍可手动检查。Windows 默认不开自动检查；Mac 会使用 Sparkle 的更新许可提示。签名或校验失败时停止更新，不提供跳过校验的选项。

## 版本与下载

每次公开发布都提升 VERSION 的数字版本，例如 1.5.0 → 1.5.1，测试版也一样。不要把不同内容重复发布为相同数字版本。Mac 的 CFBundleVersion 与 VERSION 一致，避免本机和云端时区导致版本比较出错。

更新文件放在 GitHub Releases；Mac 更新清单是 `updates/macos.xml`，Windows 的最新清单是 `updates/windows.json`，正式版清单是 `updates/windows-stable.json`。发布文件完成后再更新清单。预留 R2 下载地址，不会自动开通账户或产生托管费用。

常规更新希望控制在 30 MB 以内，但这是实测目标。更新模型、FFmpeg、运行库或很久未更新时，下载可能明显变大。需要保留旧版安装包用于生成和检查增量，固定构建依赖也有助于减少无意义变化。

## 发布者准备

- Mac 需要 Ed25519 更新签名私钥；Windows 清单使用独立 RSA 私钥。源码只保存公钥，私钥不要提交或作为 Release 附件上传。
- 发布工具读取私钥文件，生成签名与增量到新建的暂存目录，不直接发布。
- 更新签名完全在本机执行，私钥不上传 GitHub，不配置 Actions Secrets。云端可以构建普通安装包；签名更新文件由本机准备并核验后，再上传公开文件。不要把私钥发到聊天、日志或发布附件。
- Apple Developer ID 签名、公证与更新包签名是两回事。目前先做开发与本地验证；没有公证时，Mac 首次安装限制仍然存在。
- 只有安装包、对应源码和校验文件核对完成后，才发布签名更新清单。先用两版测试安装包验证真实升级，再开放给用户。

## 本地发布工具

先安装 `scripts/requirements-updates.txt` 中的构建依赖。Mac 运行 `scripts/prepare_macos_update.py --help`，Windows 运行 `scripts/prepare_windows_update.py --help` 查看参数。原始安装包不覆盖，所有生成文件进入新的输出目录。

本地公钥配置位于 SharedResources/Updates/config.json。当前候选包预设了公开更新地址，但在线清单尚未发布，因此本地包检查更新可能提示失败；发布时需最后开放清单。`enabled=false` 可用于关闭联网更新，只保留手动下载入口。


## 本地验证与发布顺序

先构建两个不同数字版本，在隔离目录做升级、失败兜底与重启测试。Mac 可以用 `BIRDLOCK_UPDATE_CONFIG` 指定只含公钥的测试配置，Windows 构建也支持这个变量。配置文件只决定公开更新地址与公钥，不放私钥。

Mac 把旧版和新版的应用 ZIP 交给 `prepare_macos_update.py`。已有在线清单时加 `--existing-feed`：工具先验证旧清单签名，发布测试版时保留上一正式版的条目，再重新签名。旧包 URL 保持原地址，不改成新 Release 的路径。Windows 给 `prepare_windows_update.py` 传新版 ZIP 和 `--previous` 旧版 ZIP，会生成完整包、文件级增量、签名清单和流量报告。正式版的 windows-stable.json 与最新清单一致。发布测试版时用 `--existing-stable-feed` 保留已签名的正式版清单。只有首次开放、还没有旧清单时用 `--initial-release`；此时正式版入口返回签名后的测试版信息，客户端会过滤它，显示暂无可用正式版。Mac 首次开放清单同样用 `--initial-release`，后续传 `--existing-feed`，防止遗漏正式版。

所有签名都在本机完成。先核对生成文件，再上传普通安装包、完整更新包和增量包到同一个 Release；确认资产下载与签名后，最后更新源码仓库里的清单。当前工具只准备本地文件，不执行上传，也不改线上清单。发布仍由我确认。

Windows 安装时保留 `.previous-…` 旧目录，失败版本放在 `.failed-…`。确认新版能正常使用后可以手动清理；程序不会自动删除这些回滚材料。遇到突然断电、更新器被强行结束或杀毒软件持续占用文件时，可能需要从旧目录恢复或重新解压完整包。日常设置和缓存都在 `data`，重新安装前请保留它。修改模型和运行库通常会增大下载量。

上传前运行 `scripts/verify_update_release.py`，用源码内公钥重新核验签名清单、更新包、内部文件清单与版本。这个检查不读取私钥，也不上传文件。`--output` 保存只含公开文件名、大小和 SHA256 的检查回执。
