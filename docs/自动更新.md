# 自动更新

BirdLock 从 1.5.0 起提供软件内更新，线上更新源已开放。第一次需要手动安装带更新功能的版本，旧版无法凭空获得更新器。之后可以在软件里检查、下载并重启安装新版。照片识别和视频合成依然不需要联网。

## 两个平台怎么更新

Mac 使用 [Sparkle 2](https://sparkle-project.org/documentation/)。更新包和更新清单都签名。清单里同时提供增量包时优先下载增量，否则使用完整包；当前 `updates/macos.xml` 只提供完整包。安装过程由 Sparkle 管理，正在分析或导出时暂缓检查和重启。

Windows 使用独立的小型更新器，利用系统的 .NET Framework 4.8，不额外打包一套 Python。先验证清单签名，再下载和校验每个文件。支持文件级增量、完整包兜底和下载续传。新版暂存完成后才退出旧版并替换程序，启动失败时恢复旧版。`data` 和不属于程序文件清单的用户文件保留在原位置。含目录链接或无法写入的目录会停止更新，请改用手动安装。

两端都可以选择接收测试版。关闭自动检查后，仍可手动检查。Windows 默认不开自动检查；Mac 会使用 Sparkle 的更新许可提示。签名或校验失败时停止更新，不提供跳过校验的选项。

## 更新源

1.10.0 之后的版本起，检查和下载更新会按顺序尝试一组更新源。默认顺序是 GitHub、BirdLock 镜像（`https://3rd.0x01.page/birdlock/update-api/`）。Mac 在 BirdLock 菜单选择「更新源…」，Windows 在更新窗口点「更新源…」，可以调整顺序、添加或删除源，也可以恢复默认。至少保留一个源。没有改过列表时，跟随每个版本内置的默认值。

- 检查时用第一个能返回有效签名清单的源。Windows 下载时先用这个源，失败后按列表顺序换其他源，再试清单里签名的备用地址。Mac 同时探测各个源，选列表中最靠前、清单和最新安装包都能访问的源，交给 Sparkle 检查和下载。
- 所有源的清单和安装包都用软件内置公钥验证签名或 SHA256，来源不影响可信度。不可靠的源最多导致检查不到更新，不能装入未经签名的程序。添加的源能看到请求者 IP 和 User-Agent。
- 1.10.0 及更早版本只认 GitHub。需要先通过 GitHub 或镜像站手动下载，安装一次带更新源的版本。
- Mac 的 Sparkle 没有改写更新说明地址的接口，使用镜像时弹窗里的远程更新说明可能加载失败，不影响下载和安装。安装后软件内的「本次更新说明」照常可看。

### 合法更新源标准

GitHub 是内置源：清单取自 `updates/`，安装包使用签名清单里的 Release 地址。其他源是一个 HTTPS 基址 `B`，不带账号、查询参数和 `#`，以 `/` 结尾，并提供：

| 路径 | 内容 |
|---|---|
| `B/macos.xml`、`B/windows.json`、`B/windows-stable.json` | 与 `main` 分支 `updates/` 下同名文件逐字节一致。缓存不超过 5 分钟 |
| `B/download/<tag>/<asset>` | 与 `https://github.com/cyandee/BirdLock/releases/download/<tag>/<asset>` 逐字节一致。`<tag>` 原样保留，例如 `v1.5.0-beta.1`，不能由版本号推算 |

- 支持 `HEAD` 和 `Range`。部分请求返回 206，`Content-Range` 必须是 `bytes <起>-<止>/<总长>`，Windows 用它续传。
- 不改写内容。请求不带 `Accept-Encoding` 时返回原始字节，不做压缩、代码精简或图片优化。
- 不存在的文件返回 404，不返回落地页。重定向只能指向 HTTPS。
- 不要拦截 `BirdLock-Updater/1`、`BirdLock/<版本>` 或 Sparkle 的 User-Agent。

客户端把签名清单中以 `https://github.com/cyandee/BirdLock/releases/download/` 开头的地址改写为 `B/download/` 加其余部分。这个前缀和默认源列表在 `SharedResources/Updates/config.json`。BirdLock 镜像把整个更新接口放在 `/birdlock/update-api/` 下，与已发布的永久下载链接 `/birdlock/latest/{mac,win}` 和 `/birdlock/<tag>/{mac,win}` 互不影响。

`scripts/check_update_source.py <B>` 按这个标准检查一个源：验证三份清单的签名并与 GitHub 逐字节比对，对清单引用的每个安装包检查 `HEAD`、尾部 `Range`，并下载 16 MB 以内的文件核对签名或 SHA256，最后确认缺失文件返回 404。加 `--full-limit 1000000000` 会完整核对大包。脚本只读公开文件和公钥。

## 版本与下载

每次公开发布都提升 VERSION 的数字版本，例如 1.5.0 → 1.5.1，测试版也一样。不要把不同内容重复发布为相同数字版本。Mac 的 CFBundleVersion 与 VERSION 一致，避免本机和云端时区导致版本比较出错。

更新文件放在 GitHub Releases；Mac 更新清单是 `updates/macos.xml`，Windows 的最新清单是 `updates/windows.json`，正式版清单是 `updates/windows-stable.json`。发布文件完成后再更新清单。预留 R2 下载地址，不会自动开通账户或产生托管费用。

常规更新希望控制在 30 MB 以内，但这是实测目标。更新模型、FFmpeg、运行库或很久未更新时，下载可能明显变大。需要保留旧版安装包用于生成和检查增量，固定构建依赖也有助于减少无意义变化。

## 发布者准备

- Mac 需要 Ed25519 更新签名私钥；Windows 清单使用独立 RSA 私钥。源码只保存公钥，私钥不要提交或作为 Release 附件上传。
- 发布工具读取私钥文件，生成签名与增量到新建的暂存目录，不直接发布。
- 更新签名完全在本机执行，私钥不上传 GitHub，不配置 Actions Secrets。云端可以构建普通安装包；签名更新文件由本机准备并核验后，再上传公开文件。不要把私钥发到聊天、日志或发布附件。
- Apple Developer ID 签名、公证与更新包签名是两回事。目前没有做 Apple 公证，Mac 首次安装限制仍然存在。
- 只有安装包、对应源码和校验文件核对完成后，才发布签名更新清单。先用两版测试安装包验证真实升级，再开放给用户。

## 本地发布工具

先安装 `scripts/requirements-updates.txt` 中的构建依赖。Mac 运行 `scripts/prepare_macos_update.py --help`，Windows 运行 `scripts/prepare_windows_update.py --help` 查看参数。原始安装包不覆盖，所有生成文件进入新的输出目录。

本地公钥配置位于 SharedResources/Updates/config.json。1.5.0 已预设公开更新地址，线上清单已开放。1.5.0及更新版本可直接更新至1.10.0；新版本会在首次启动后显示更新说明，并在帮助菜单提供再次查看入口。普通启动不重复显示，首次安装不会误报升级成功。当前没有更高数字版本时会显示暂无更新。`enabled=false` 可用于关闭联网更新，只保留手动下载入口。


## 本地验证与发布顺序

先构建两个不同数字版本，在隔离目录做升级、失败兜底与重启测试。Mac 可以用 `BIRDLOCK_UPDATE_CONFIG` 指定只含公钥的测试配置，Windows 构建也支持这个变量。配置文件只决定公开更新地址与公钥，不放私钥。

Mac 把旧版和新版的应用 ZIP 交给 `prepare_macos_update.py`。已有在线清单时加 `--existing-feed`：工具先验证旧清单签名，发布测试版时保留上一正式版的条目，再重新签名。旧包 URL 保持原地址，不改成新 Release 的路径。Windows 给 `prepare_windows_update.py` 传新版 ZIP 和 `--previous` 旧版 ZIP，会生成完整包、文件级增量、签名清单和流量报告。正式版的 windows-stable.json 与最新清单一致。发布测试版时用 `--existing-stable-feed` 保留已签名的正式版清单。只有首次开放、还没有旧清单时用 `--initial-release`；此时正式版入口返回签名后的测试版信息，客户端会过滤它，显示暂无可用正式版。Mac 首次开放清单同样用 `--initial-release`，后续传 `--existing-feed`，防止遗漏正式版。

所有签名都在本机完成。先核对生成文件，再上传普通安装包、完整更新包和增量包到同一个 Release；确认资产下载与签名后，最后更新源码仓库里的清单。当前工具只准备本地文件，不执行上传，也不改线上清单。发布仍由我确认。

Windows 安装时保留 `.previous-…` 旧目录，失败版本放在 `.failed-…`。确认新版能正常使用后可以手动清理；程序不会自动删除这些回滚材料。遇到突然断电、更新器被强行结束或杀毒软件持续占用文件时，可能需要从旧目录恢复或重新解压完整包。日常设置和缓存都在 `data`，重新安装前请保留它。修改模型和运行库通常会增大下载量。

上传前运行 `scripts/verify_update_release.py`，用源码内公钥重新核验签名清单、更新包、内部文件清单与版本。这个检查不读取私钥，也不上传文件。`--output` 保存只含公开文件名、大小和 SHA256 的检查回执。
